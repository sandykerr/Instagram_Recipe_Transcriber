The pipeline should:
1. Read new recipe rows from Google Sheets.
2. Acquire enough source material from the Instagram Reel:
   - Caption text
   - Audio/narration
   - On-screen text
   - Possibly the video itself or a local screen recording
3. Determine where the actual recipe information is located.

5. Calculate nutrition when the inputs are sufficiently complete.
6. Create a Google Doc using a consistent recipe template.

10. Preserve enough intermediate data to debug errors.

This should be treated as a multimodal ETL pipeline with a human-review path,
not as one large prompt that sends an Instagram URL to an LLM.

9. VIDEO FRAME EXTRACTION AND OCR
======================================================================

On-screen text is essential because many Reels omit quantities from narration.

Proposed process:
1. Detect scene changes and/or sample frames at a configurable rate.
2. Calculate perceptual hashes.
3. Remove near-duplicate frames.
4. Detect frames likely to contain text.
5. Run OCR on the reduced frame set.
6. Preserve timestamps and frame paths/hashes.
7. Deduplicate repeated OCR text using normalized text similarity.
8. Optionally send only ambiguous, distinct frames to a vision model.

Do not send every video frame to a vision LLM.

Possible implementation ideas:
- FFmpeg scene detection
- OpenCV frame sampling
- imagehash or OpenCV perceptual hashing
- PaddleOCR, EasyOCR, Tesseract, or a vision-capable LLM
- Recipe-specific OCR normalization for:
  - tsp, tbsp, cup, oz, lb, g, kg, ml
  - fractions such as 1/2, 1/3, 1/4, 3/4
  - Unicode fractions
  - temperatures
  - line breaks and overlaid labels

Example OCR segment:

{
  "start_seconds": 2.4,
  "end_seconds": 4.1,
  "frame_path": "working/.../frame_00024.jpg",
  "text_raw": "1 tsp fennel seeds\n1 tsp garlic powder",
  "text_normalized": "1 tsp fennel seeds; 1 tsp garlic powder",
  "confidence": 0.93
}

Need tests for duplicate overlays, animated text, bad contrast, and captions
covering ingredient text.

13. DETERMINISTIC VALIDATION
======================================================================

After LLM extraction, run code-based checks.

Examples:
- Recipe has at least one component and one step.
- Major ingredients have quantities if nutrition is requested.
- Servings are present before per-serving nutrition is calculated.
- Every ingredient reference in steps exists.
- Ingredients used in steps but missing from the shopping list are flagged.
- Shopping-list ingredients never used in any step are flagged.
- Temperatures include a unit.
- "Seasonings shown on screen" without recovered OCR triggers review.
- Caption and on-screen quantities that disagree trigger review.
- Very low-confidence numbers or units trigger review.
- Duplicate ingredients are merged only when safely equivalent.
- Unrealistic quantities are flagged, not automatically changed.
- Twenty cloves of garlic may be intentional; unusual is not automatically
  wrong.

Example:

def needs_review(recipe: Recipe, report: ValidationReport) -> bool:
    return any([
        recipe.overall_confidence < 0.80,
        recipe.servings is None,
        not recipe.components,
        not recipe.steps,
        report.has_unresolved_conflicts,
        report.has_missing_major_quantities,
        any(i.confidence < 0.65 for i in recipe.all_ingredients()),
    ])

Rows that fail validation should normally become REVIEW, not ERROR.

14. NUTRITION CALCULATION
======================================================================

Nutrition should be a separate deterministic or semi-deterministic stage.

Potential data source:
- USDA FoodData Central API
- Verify current API documentation, authentication, quotas, and data fields

Suggested process:
1. Normalize each ingredient.
2. Convert amounts to grams or milliliters where possible.
3. Search the nutrition database.
4. Select a match with a confidence score.
5. Preserve the selected database item and identifier.
6. Calculate total-recipe nutrition.
7. Divide by known servings.
8. Store unrounded internal values.
9. Render reasonable rounded values or ranges.
10. Refuse or defer calculation when major amounts are missing.

Example match record:

{
  "ingredient_id": "ing_003",
  "query": "low fat cottage cheese",
  "selected_name": "Cottage cheese, lowfat, 2% milkfat",
  "external_id": "...",
  "grams": 226.0,
  "match_confidence": 0.87,
  "manual_override": false
}

Potential nutrients:
- Calories
- Protein
- Fiber
- Carbohydrates
- Fat

Important:
- Store source nutrition claims separately from calculated nutrition.
- Do not claim precision that the input does not support.
- If servings or major quantities are absent, include a document note instead
  of a fabricated estimate.

17. RATE LIMITING, RETRIES, AND ASYNCHRONOUS WORK
======================================================================

The worker should be resilient rather than highly concurrent.

Recommended personal-scale defaults:
- One or two recipe jobs at a time
- Batch Sheet reads and writes
- One Google Docs batch update per document where practical
- Exponential backoff with jitter for 429 and retryable 5xx responses
- Configurable maximum retries
- No unlimited LLM repair loop
- Persist intermediate artifacts between stages
- Mark every stage complete before advancing
- Use idempotent operations
- Use a processing lease so stale jobs can be reclaimed

Example state machine:

NEW
  -> WAITING_FOR_MEDIA, when no accessible media exists
  -> ACQUIRING
  -> EXTRACTING
  -> CLASSIFYING
  -> STRUCTURING
  -> VALIDATING
  -> NUTRITION
  -> RENDERING
  -> DONE

Branches:
- Any stage -> ERROR for actual processing failures
- VALIDATING -> REVIEW for incomplete/conflicting recipes
- Any stage -> SKIPPED for duplicate/non-recipe content when configured

Potential lease fields:
- processing_started_at
- processing_until
- worker_id

On startup:
- Reclaim jobs whose processing_until is in the past.
- Do not duplicate Docs for jobs that already have a doc_id.
- Save a content or schema hash for detecting changed source material.
